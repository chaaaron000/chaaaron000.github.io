사람과 AI가 같은 데이터를 고치는 콘텐츠 제작 도구를 만듭니다

기능 하나를 구현하는 것보다, 콘텐츠가 계속 늘어날 수 있는 구조를 만드는 데 집중해 왔습니다. 지금은 사람이 쓰는 편집기와 AI 에이전트가 쓰는 인터페이스를 같은 데이터 위에 세우고, 그 위에서 게임을 만들고 있습니다.

Caldera 레벨 편집기에서 일하는 방식을 그린 그림입니다. 제가 도면에 메모를 남기면, 같은 도면에 붙은 에이전트가 벽을 그립니다.

AI 작업 환경

여러 AI를 역할별로 나눠 씁니다. 아래 프로젝트들은 모두 이 방식으로 만들고 있습니다.

  1. 판단 기준을 먼저 적습니다. 저장소마다 AGENTS.md에 우선순위(내 요청, 정리 문서, 원천 자료, 코드, AI 추론 순)와 프로젝트 규칙을 둡니다.
  2. 근거와 정리를 나눕니다. 결정 기록과 자료는 raw에, 정리본은 wiki에 두어 AI가 근거를 찾아 씁니다.
  3. 대화와 작업을 나눕니다. 저와 대화하는 오케스트레이터는 일을 쪼개 브리프를 쓰고, 구현과 검수는 새 워커가 맡습니다. 브리프에는 목표, 범위, 정한 결정, 완료 기준, 보고 파일 경로를 담습니다.
  4. 보고를 믿지 않고 확인합니다. 문법 검사기, 테스트, 실제 플레이 결과로 끝을 판단합니다.
  5. 겪은 것을 남깁니다. 제 피드백과 함정은 메모 파일에 쌓아 다음 작업이 같은 실수를 하지 않게 합니다.
herdr-loadout

레벨 설계 편집기

한 층 평면도를 구조 데이터(JSON)로 두고 브라우저에서 벽, 문, 방을 편집합니다. 방과 면적은 편집할 때마다 다시 계산하고, 검사 결과를 화면에 핀으로 띄웁니다. 키 하나로 2D, 3D 탑뷰, 1인칭 사이를 오갑니다.

  • 사람과 에이전트가 같은 도면을 함께 고칩니다. 서버가 연 도면을 실시간 세션으로 쥐고, 브라우저 탭과 MCP로 붙은 에이전트가 같은 세션을 편집합니다. 고칠 곳은 도면 위 메모 핀으로 알려 줍니다.
  • 평면도를 에이전트가 직접 읽고 잽니다. floorplan-to-game-level로 도면 이미지와 PDF를 추적해 편집기로 가져오고, 게임용 FBX로 내보내 검수합니다.
  • 빌드 단계와 npm 의존성 없이 Node 22 하나로 돌아갑니다.

미션 데이터: 식별, 호출, 표시를 나누다

이름을 바꿔도 참조가 풀리지 않는 구조가 목표였습니다. 처음엔 해시를 식별자로 쓰려 했는데, AI가 해시는 내용이 바뀌면 값도 바뀐다며 GUID를 제안했고, 근거가 타당해 받아들였습니다. 여기에 Naninovel이 부르는 Name과 사람이 읽는 Title을 더해 역할을 나눴습니다.

미션 커스텀 인스펙터

기본 인스펙터에서는 GUID가 그대로 보이고 모든 필드가 한 열로 늘어서 있었습니다. 원하는 화면을 직접 스케치해 Codex에 구현을 맡기고, 아쉬운 곳은 구체적으로, 좋은 곳은 이유까지 전하며 고쳐 나갔습니다. GUID를 복사하고 대상을 다시 찾던 작업이 사라졌습니다.

Unity 전에 웹으로 먼저 검증

보고서, 조사 계획, 시간, 결과, 제안이 한 흐름에 얽혀 있어, Unity UI로 바로 만들면 수정 비용이 컸습니다. Penpot으로 화면을 설계하고 React와 TypeScript 프로토타입, Vitest로 상태 로직부터 검증했습니다.

시나리오 자동 검증

.nani 스크립트는 C#이 아니라서 Unity 컴파일이 성공해도 잘못된 커맨드가 남을 수 있습니다. Naninovel 공식 언어 서버를 꺼내 에이전트 편집기에 연결하고, 의도적 오류 파일로 검사기 자체도 테스트했습니다.

Blackboard 시스템

콤보 횟수, 약품 사용 횟수처럼 마스코트가 반응해야 할 상태가 계속 늘어날 것이 보여서, 게임 로직과 반응 시스템이 서로를 직접 알지 않게 했습니다. 로직은 Blackboard에 값만 기록하고, 반응 쪽은 값이 바뀌었다는 알림만 받아 평가합니다.

  • 키마다 INT, FLOAT, BOOL, STRING 중 하나를 스키마로 고정하고, 다른 자료형 값은 거부
  • 시작값과 런타임 값을 분리해 스테이지마다 초기화
  • Unity 직렬화 한계 때문에 object 대신 자료형별 값을 명시적으로 보관

조건 트리와 반응 테이블 에디터

명일방주 모작을 하며 원작 버프 데이터가 조건을 트리로 조합하는 걸 보고, 그 방식을 가져왔습니다. 값 비교 6가지, And, Or, Not, AlwaysTrue, IsValueChanged 노드를 조합해 반응 조건을 데이터로 만듭니다. 스키마에 등록된 키만 고를 수 있고, 고른 키의 자료형에 맞춰 입력 칸이 바뀌는 커스텀 인스펙터도 만들었습니다.

콤보 3, 5, 7, 10회 반응을 새 판단 코드 없이 조건 조합만으로 추가했고, 같은 구조를 「화면 건너편의 너」에서 다시 썼습니다.

Photon Fusion 전환 제안

기존 Unity RPC 방식은 오류 원인을 추적하기 어렵고, 상태와 애니메이션 동기화가 자주 어긋났으며, 기능 하나를 붙이는 데 시간이 많이 들었습니다. 이미 만든 기능을 다시 만드는 비용과 같은 방식으로 계속 확장할 때 반복될 비용을 견줘 근거를 정리했고, 팀 동의를 얻어 Fusion으로 옮겼습니다.

몬스터 FSM 리팩터링

팀원이 만든 몬스터 행동 알고리즘을 분석해 대기, 경계, 추적, 공격 네 상태로 나누고, 동작을 그대로 지킨 채 Fusion 상태 머신으로 옮겼습니다. 새로 만들기보다 기존 코드가 왜 그렇게 동작하는지부터 이해하는 걸 원칙으로 삼았습니다.

Vivox 음성 채팅

Photon 세션 이름으로 Vivox 위치 기반 채널을 정해 참가하고, 플레이어 위치를 음성 처리에 반영했습니다. 설정 화면에서 마이크와 출력 장치를 바꿀 수 있게 연결했습니다.

출시 전 난이도 조정

1년 내내 플레이한 팀의 감각이 무뎌졌다고 보고 외부 플레이테스트를 맡겼습니다. 피드백 반영 폭을 두고 의견이 갈렸을 때, 도입부는 유지하고 마지막 스테이지만 올리는 쪽으로 합의했습니다.

기여 범위: 몬스터 초기 알고리즘은 팀원 구현이고, 상태 머신 리팩터링과 Vivox 연동 두 커밋이 제 몫입니다. 커밋 단위 구분은 코드 아카이브에 있습니다.
