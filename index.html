01Caldera개발 중

평면도에서 걸어 들어갈 수 있는 레벨까지

협동 생존 게임. 인디 규모로 어디까지 손을 뻗을 수 있는지 확인하는 프로젝트입니다.

레벨 설계 편집기

한 층 평면도를 구조 데이터(JSON)로 두고 브라우저에서 벽·문·방을 편집합니다. 방과 면적은 편집할 때마다 다시 계산하고, 검사 결과를 화면에 핀으로 띄웁니다. T와 Tab 한 번으로 2D, 3D 탑뷰, 1인칭(Three.js) 사이를 오갑니다.

  • 사람과 에이전트가 같은 도면을 함께 고칩니다. 서버가 연 도면을 실시간 세션으로 쥐고, 브라우저 탭과 MCP로 붙은 에이전트가 같은 세션을 편집합니다. 에이전트에게 고칠 곳을 알려줄 때는 도면 위에 메모 핀을 꽂습니다.
  • 평면도를 에이전트가 직접 읽고 잽니다. 직접 만든 floorplan-to-game-level 스킬로 도면 이미지·PDF를 추적해 편집기로 가져오고, 게임용 FBX로 내보내 검수합니다.
  • 빌드 단계와 npm 의존성 없이 Node 22 하나로 돌아갑니다.

제가 정한 것

  • 도면 데이터 구조와 편집 규칙
  • 사람과 에이전트가 한 세션을 공유하는 구조
  • 검사 항목과 레벨 수치 기준

AI에게 맡긴 것

  • 편집기 구현과 3D·1인칭 뷰어
  • 평면도 추적과 배치 초안
  • FBX 내보내기 검수 스크립트 실행

02PerfectHer개발 중

혼자서 기획·개발·아트까지 돌리는 파이프라인

심리적 공포 비주얼 노벨. 사건을 살피고 추리하는 게임플레이를 Naninovel과 Unity로 만들고 있습니다.

사건 데이터 편집 시스템

  • 사람용 편집기와 에이전트용 CLI가 같은 저장 경로를 씁니다. 사건마다 쓰기 잠금을 잡고, 읽은 판(해시)과 지금 파일을 견줘 그 사이 바뀌었으면 쓰지 않습니다.
  • 원본 하나에서 사본을 한 묶음으로 만듭니다. 저장할 때마다 웹 시안용 JS 사본과 Unity용 사본을 함께 씁니다. 시안에서 확인한 사건이 그대로 게임에 들어갑니다.
  • git에서 고친 줄만 보이도록 키 순서와 줄 바꿈 규칙을 고정했습니다.

코드 리뷰 대신 QA 플레이

다른 모델에게 코드 리뷰를 맡겨 봤지만 실제 버그는 거의 잡지 못했습니다. 그래서 QA 전담 에이전트가 Unity Play 모드에서 직접 플레이하게 바꿨습니다. 정답 길과 오답 길을 끝까지 가 보고, 대사 중간 저장·연타·되감기 같은 엇나간 조작을 해 본 뒤 버그를 심각도별로 보고합니다. 잡은 버그는 재현 절차를 회귀 스크립트로 남깁니다.

회귀 27개 경로대사 순서·끝 상태·저장 후 불러오기·콘솔 오류를 매번 비교
QA 왕복 최대 3번그 뒤에도 남은 문제는 사람이 판단

AI 아트 파이프라인

GPU가 하나라 ComfyUI 생성과 Blender 렌더가 부딪힙니다. 작업마다 사용권을 받아 줄을 서게 하는 GPU 큐를 만들어, 에이전트들이 서로 기다리며 GPU를 나눠 씁니다.

제가 정한 것

  • 사건 데이터 꼴과 저장 규칙
  • QA 흐름과 버그 심각도 기준
  • 아트 방향, 시안 선택과 반려

AI에게 맡긴 것

  • 편집기·CLI·Unity 기능 구현
  • QA 플레이와 회귀 스크립트 작성

03AI 작업 환경

여러 AI를 역할별로 나눠 쓰는 방식

위 두 프로젝트는 모두 이 방식으로 만들고 있습니다.

  1. 판단 기준을 먼저 적습니다. 저장소마다 AGENTS.md에 우선순위(내 요청 > 정리 문서 > 원천 자료 > 코드 > AI 추론)와 프로젝트 규칙을 둡니다.
  2. 근거와 정리를 나눕니다. 결정 기록과 자료는 raw에, 정리본은 wiki에 두어 AI가 근거를 찾아 씁니다.
  3. 대화와 작업을 나눕니다. 저와 대화하는 오케스트레이터는 일을 쪼개 브리프를 쓰고, 구현과 검수는 새 워커가 맡습니다. 브리프에는 목표, 범위, 정한 결정, 완료 기준, 보고 파일 경로를 담습니다.
  4. 보고를 믿지 않고 확인합니다. 문법 검사기, 테스트, 실제 플레이 결과로 끝을 판단합니다.
  5. 겪은 것을 남깁니다. 제 피드백과 함정은 메모 파일에 쌓아 다음 작업이 같은 실수를 하지 않게 합니다.

herdr-loadout

Herdr 플러그인 · Node

어떤 역할에 어떤 도구·모델·추론 강도를 쓸지 프로필로 등록해 두고, 오케스트레이터가 적은 컨텍스트로 조회해 워커를 띄웁니다. 터미널 UI와 데스크톱 앱 편집기를 함께 지원합니다.

Blackboard 시스템

콤보 횟수, 약품 사용 횟수처럼 마스코트가 반응해야 할 상태가 계속 늘어날 것이 보여서, 게임 로직과 반응 시스템이 서로를 직접 알지 않게 했습니다. 로직(GameManager, CardManager)은 Blackboard에 값만 기록하고, 반응 쪽은 값이 바뀌었다는 알림만 받아 평가합니다.

  • 키마다 INT·FLOAT·BOOL·STRING 중 하나를 스키마로 고정하고, 다른 자료형 값은 거부
  • 시작값과 런타임 값을 분리해 스테이지마다 초기화
  • Unity 직렬화 한계 때문에 object 대신 자료형별 값을 명시적으로 보관

조건 트리와 반응 테이블 에디터

명일방주 모작을 하며 원작 버프 데이터가 조건을 트리로 조합하는 걸 보고, 그 방식을 가져왔습니다. 값 비교 6가지, And·Or·Not, AlwaysTrue, IsValueChanged 노드를 조합해 반응 조건을 데이터로 만듭니다.

스키마에 등록된 키만 고를 수 있고, 고른 키의 자료형에 맞춰 입력 칸이 바뀌는 커스텀 인스펙터도 만들었습니다.

이미지 예정 · 반응 테이블 에디터 캡처 media/greenclean-editor.jpg

콤보 3·5·7·10회 반응을 새 판단 코드 없이 조건 조합만으로 추가했고, 같은 구조를 「화면 건너편의 너」에서 다시 썼습니다.

Photon Fusion 전환 제안

기존 Unity RPC 방식은 오류 원인을 추적하기 어렵고, 상태와 애니메이션 동기화가 자주 어긋났으며, 기능 하나를 붙이는 데 시간이 많이 들었습니다. 이미 만든 기능을 다시 만드는 비용과, 같은 방식으로 계속 확장할 때 반복될 비용을 견줘 근거를 정리했고, 팀 동의를 얻어 Fusion으로 옮겼습니다.

몬스터 FSM 리팩터링

팀원이 만든 몬스터 행동 알고리즘을 분석해 대기·경계·추적·공격 네 상태로 나누고, 동작을 그대로 지킨 채 Fusion 상태 머신으로 옮겼습니다. 새로 만들기보다 기존 코드가 왜 그렇게 동작하는지부터 이해하는 걸 원칙으로 삼았습니다.

Vivox 음성 채팅

Photon 세션 이름으로 Vivox 위치 기반 채널을 정해 참가하고, 플레이어 위치를 음성 처리에 반영했습니다. 설정 화면에서 마이크와 출력 장치를 바꿀 수 있게 연결했습니다.

출시 전 난이도 조정

1년 내내 플레이한 팀의 감각이 무뎌졌다고 보고 외부 플레이테스트를 맡겼습니다. 피드백 반영 폭을 두고 의견이 갈렸을 때, 도입부는 유지하고 마지막 스테이지만 올리는 쪽으로 합의했습니다.

기여 범위: 몬스터 초기 알고리즘은 팀원 구현이고, 상태 머신 리팩터링과 Vivox 연동 두 커밋이 제 몫입니다. 커밋 단위 구분은 코드 아카이브에 있습니다.

미션 데이터: 식별·호출·표시 분리

이름을 바꿔도 참조가 풀리지 않는 구조가 목표였습니다. 처음엔 해시를 식별자로 쓰려 했는데, AI가 해시는 내용이 바뀌면 값도 바뀐다며 GUID를 제안했고, 근거가 타당해 받아들였습니다. 여기에 Naninovel 호출용 Name과 사람이 읽는 Title을 더해 역할을 나눴습니다.
